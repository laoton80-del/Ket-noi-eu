## 2. Merchant-only authority revalidation

Before `claimed → providerPending`, inside a Serializable transaction the gateway:

1. Loads the exact attempt and verifies lease owner + non-expired lease
2. Loads the exact request and requires `status = inProgress`
3. Reloads current `MerchantProfile` by attempt snapshot profile id
4. Requires active profile, exact profile/tenant/owner match, merchant provenance
5. Rejects consumer, legacy, and malformed provenance
6. Ignores envelope tenant/profile fields

Denied cases create no provider preparation, call, key, or outcome mutation. Request status is never finalized in D3A.

## 4. Preparation transaction

Serializable, closed before any adapter call:

```text
load attempt → lease + claimed checks → revalidate authority
→ derive key → claimed → providerPending
→ persist provider name / operation / key / providerStartedAt
→ COMMIT
```

No `VionaRequest` status transition. No completion events/audits.

## 5. Provider-outcome recording

Separate Serializable transaction after adapter returns:

| Adapter result | Attempt state |
|---|---|
| known success | `providerSucceeded` (+ digest / external-ref digest) |
| known failure | `providerFailed` (+ bounded failure class/digest) |
| timeout / response-loss / throw | `outcomeUncertain` |

Updates require exact attempt id, `providerPending`, matching provider/operation/key, and lease owner. Zero-row updates surface as `outcome_record_conflict`.

## 6. Uncertain-outcome / no blind retry

- Timeout and connection-loss map to `outcomeUncertain`
- Duplicate gateway runs against `providerPending` / recorded / terminal states fail closed **without** invoking the adapter
- No automatic provider re-invoke
- Recovery reserved for later Pack40D3B (unimplemented)
